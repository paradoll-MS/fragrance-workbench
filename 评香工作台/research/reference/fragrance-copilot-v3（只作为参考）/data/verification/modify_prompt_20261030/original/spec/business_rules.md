# 项目理解的业务边界（2026-10-29 校正）

这是已确认的业务规则，优先于历史模型结果。历史标签和字段位置都可能是旧模型错误，不能拿来证明自己。

1. 客户给的前中后调、香调表、AI拼出的香材组合、竞品三调均是参考资料，只辅助理解B/C，不得逐词映射A1/A2/A3或当主韵硬筛。A代表真正想选的主体气味/主韵，必须另有客户明确的气味目标或明确主韵依据。即使三调里有雪松、罗勒、薄荷，也不因此选出这些A。客户另说“柑橘果香更适合”才可据这句选择相应A，不能顺带把配角全部提升为主韵。没有独立依据时A允许为空。主辅关系必须保留。B是感受/风格，C是对应内部品类的定位/场景/体验，包括由参考三调辅助理解出的含义。
2. customer_requirements专指额外文件/证明/认证/特殊对外宣称，category只能是document/certificate/claim。例：要求提供IFRA证明、指定检测报告、清真认证文件、天然来源证明、需要支持某项对外宣称。普通气味方向、不要甜、留香/扩散、DPM相容、加香量、稳定性条件、样品数量和交期均回到普通简报字段，不能仅因“客户提出”就列为额外。闻起来天然≠天然来源宣称；留香久≠24小时证明。没有额外要求就留空，不为填表制造条目。混合段落拆出真正的文档/宣称，其它内容留普通字段。
3. 普通信息分别进入product/scent/commercial/compliance/deliverables；客户企业、联系人、总体交期/对接进入项目层，局部交期与专属条件进入适用子项目。requirement_register仅是带来源的普通条件/待复核记录，不属于额外要求，不是额外红色检查清单。
4. 参考信息必须标明来源和用途；销售AI建议不能当客户已确认的配方。不要把对标等同仿香；不要将缺省信息编成明确要求。三调保存在scent.top/middle/base或note_references，主韵在scent.main_accord，二者不可混写。
5. 工单必须保留普通需求、额外证明/宣称及来源，两类不能互相吞掉。来源、目标、推断、已验证结果分别记录；原件和历史永不改写。


## 不能反向过度保守

“不能从三调逐词给A”不等于“香材组合一律是参考”或“必须出现主韵二字才给A”。客户直接说希望闻到海水、金属、纸张，或者要求以茶、咖啡、墨水等味道为主要方向，这是明确气味目标，应按各目标所属子项目选择有依据的A。只有竞品三调表、前中后调、被标作参考的AI提案等才限于BC。不得为了回避错误把这些明确目标的A全部留空。原有模型A为空不是客户要求为空，不能照抄旧结果。

## 映射与必选产品不能遗漏

简报已提取的感受、主体方向和产品定位，应进入相应ABC语义映射；空数组不代表已经做完映射。真正缺上下文或词表不覆盖的域，需要具体原因及来源，不能伪装成完成推荐。没有ABC的品牌语义推荐不能用全库零分列表充当结果。
推荐组合中明确必须包含的具体产品是独立找香需求，不只是参考；应有并行find_product入口，和其余风格选型共享项目总数量及供样方式。后期可能拓展的用途保留为未来意向，不提升为当前产品或已成立的特殊安全宣称。
