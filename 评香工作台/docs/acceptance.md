# Acceptance ／ 本机验收

这份文件回答一个问题：现在能证明什么，还不能证明什么。不写「已完成」的空话。

## 1. 自动验收

```
python -X utf8 -m unittest discover -s tests -t .
```

65 条，全部不发外部请求，使用 `data/` 下的固定库文件。

- `test_domain`：规范化、价格区间、市场别名、版本比较。
- `test_brief`：三条方向与合规原文不丢、共享字段继承、打标依据必须落在原文、失败退回词面、检索用目标标签。
- `test_rules`：规则装载、品类与市场默认、条件触发、覆盖说明。
- `test_ranking`：查询归一、硬筛、评分、文字解析、精确产品。
- `test_workflow`：阶段动作、开发链、放行严格度、证据复用、问题恢复、并发修订。
- `test_http`：真实起服务，健康检查、静态文件、越权路径、生命周期、错误码。
- `test_acceptance`：两条完整业务链路，见下。

`test_acceptance` 的两条：

1. 选香到客户交付：资料 → 方向 → 选香 → 11 条要求（出处、口径、部门齐全）→ 派发 → 回执 → 正式放行 → 备样 → 寄样 → 项目完成。断言释放记录、寄样记录、计数。
2. 仿香到入库再回父项：分析 → 调香 → 退回一次 → 验收 → 一查 → 入库放行 → 入库 → 回父项 → 二查复用 11 条证据 → 正式寄样 → 项目完成。断言试作与验收记录、证据改键、父项复用。

## 2. 手工验收

启动后打开 `http://127.0.0.1:18761/project.html?id=1`，示例项目已经走到完成。按下面的顺序看：

1. 项目头部：3/3 目标位、无待处理；3 个子项都已完成。
2. 第一个方向：检查清单 v2、11 条通过；两条放行记录（初寄、正式）；两条寄样记录；三个部门任务都带外部编号。
3. 第二个方向：父项「启动仿香」，子项「竞品样复刻」；子项里有分析、调香、入库三类任务，试作与 GC。
4. 子项检查清单是「入库」范围，父项是「客户交付」范围；父项那 11 条来自子项证据，没有重复派发。
5. 打开 `mock.html`：能看到上述任务与回执；改默认回执后新任务会按新规则返回。
6. 打开 `select.html?q=白茶 200 以内 洗发水`：结果带价格、标签、关联产品，线索另列。

再点一遍「新建项目」，导入一份文字资料，走 `manual_draft → confirm_draft → plan → build_checks`，确认缺字段不会阻断：市场、价格、用量都可以空着，只在检查清单的覆盖说明里提示。

## 3. 对验收参考的逐条状态

数字对应 [验收参考](验收参考.md) 的章节。

1. **Parse 需求理解**：资料读取、段落定位、两层 brief、方向草案、字段修订已实现。蓝甘菊真实 PDF 跑通：3 条方向、人群 6-12 岁、4 条法规、7 条禁用物、表稳说明与闪点都保留。多产品拆分靠「草案 + 人工确认」，不自动承诺；真实 brief 的提取质量仍没有系统评测。
2. **Context 语境**：Subproject／Round／Goal／Slot 与父子关系齐备，`round.brief` 留两层原文，`goal.fields` 留展开结果；「上一款」「第二支」这类指代没有做语义解析，需要人选参照。
3. **Targeting 推荐目标**：`tag_direction` 输入品类、人群、市场、香气原文与要求，候选带 C 左侧判定指导；模型只选 C，A/B 由字典展开。项目页显示标签、依据与未映射，选香页按目标标签筛选。模型不可用时退回词面匹配，不阻断。
4. **Recommendation 筛选排序**：模式、品类、价格、标签、品牌、产品、线索与诊断都有；目标检索已接打标结果。历史工单回放没有做，无法回答「历史实推为什么被选中」。
5. **Workflow 业务流程**：选香、仿香、创香、改香、精确找香五条路径；开发回父项；入库与客户交付终点分开。由 `test_acceptance` 与 `test_workflow` 覆盖。
6. **Checking 检查**：规则生成、条件合并、分部门派发、证据复用、放行判定齐备；部门回执目前是整组通过/退回，没有逐项录入。
7. **State 状态机**：六阶段、Issue 自动生成与自动恢复、暂存恢复、修订冲突、重复回执拒绝，均有测试。
8. **Dispatch 适配层**：模拟中台有独立页面；任务带对象、要求、口径、版本；回执回流推进流程；业务层只认 `PlatformPort`。多部门并行与乱序回执由任务独立支撑，但没有专门的压力测试。
9. **LLM 模型**：两个节点、模型与端点可配、禁用思考、超时与重试提示；图片走视觉转写。每次真实请求写入 `llm_call`，项目页「模型调用」可回看 system/user/返回；没有多模型对比记录，也没有响应时间统计。
10. **UI 体验**：三个页面、动作名即业务动作、错误带对象与下一步；没有真人点击验收，本机浏览器自动化被权限拦住。
11. **Feedback 回流**：人工改标签写 `asset_edits` 并影响后续推荐；需求修正走新草案并保留原文；检查证据沉淀为香精资产。历史选香与客户反馈的沉淀没有做。
12. **Architecture 结构**：分层、依赖方向、唯一写库入口、文档与实现对应；`docs/` 与代码同步更新。
13. **End-to-end 综合案例**：见第 4 节的覆盖表。
14. **Review 反思**：见 [取舍](decisions.md)；真实案例的复盘要等有真实资料。

## 4. 综合案例覆盖

验收参考列了 12 类案例，当前状态：

- 已覆盖：简单推荐（案例 1）、多产品多子项（3，手工草案）、精确检索（4）、对香与仿香（5）、多次调香与验收（6）、部分历史检查核销（8，证据复用）、无客户交付的入库终点（12，开发子项）、真实 PDF 的三方向提取与打标（案例 2 的加强版）。
- 部分覆盖：信息少需理解品牌（2，打标已可用）、初寄后继续推荐（9，初寄回执后可继续，但没有「客户反馈再推荐」入口）、信息缺失与等待（11，Issue 与暂存支撑，但没有专门脚本）。
- 未覆盖：同项目内选香＋创香＋改香并行（7）、多模态资料（10）、复寄轮（9 的另一半）。

未覆盖的共同原因是缺真实资料与真实中台，不是结构缺失。补的时候优先补 10 与 9，因为它们最容易暴露字段设计问题。

## 5. 已知缺口

- 部门回执整组通过，不能逐项回流。
- 初寄样之后没有「客户反馈」对象，只能记录复寄。
- 没有迁移脚本，改表要先备份。
- 模拟中台的库存与报价是常量，不能通过页面改。
- 真实中台未接，`PlatformPort` 只有 Mock 实现。
