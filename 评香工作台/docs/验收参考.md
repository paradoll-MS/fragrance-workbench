# Acceptance Reference / 验收参考

## 0. 验收的基本方式

深入案例分析优先于数据。充分利用真实项目工单、历史选香记录、客户反馈及附件，以一个评香人员实际使用平台的视角进行测试。

不要仅仅验证某个函数能够运行、某个页面能够打开、某个字段能够输出，而是思考输出的内容是否有价值、是否符合业务常理、是否足以支撑下一步操作。

对于发现的问题，尽可能追溯到具体的对象、函数、数据、Prompt、模型或流程设计，并思考是否存在符合逻辑的改进方法。不要为了拟合某一个案例而引入缺乏普适性的规则。

## 1. Parse / 需求理解与信息提取

1. 是否能够像 copilotV3 一样充分、准确地提取项目的主要内容，同时保留对后续工作有价值的信息。
2. 是否有能够充分流转信息的 Schema 和字段，是否能够正确判定项目入口、需求类型、Solution 及相关字段值。
3. 面对一份包含多个产品、多种要求的复杂 brief，是否能够合理拆分子项目，并将公共要求正确分配给各个子项目。
4. 是否能够理解客户语言中的隐含意图，区分硬性要求、偏好、背景描述和参照信息，而不是机械地提取关键词。
5. 是否能够正确区分指定产品、品牌风格参考、实物对香、原创概念和针对已有香精的修改要求。
6. 是否会因为客户没有提供价格、相似度、具体数量等暂时不影响推进的信息而产生不必要的阻塞。
7. LLM 提取出的内容是否便于评香检查和修改，是否能让评香迅速意识到有哪些信息被遗漏或误解。
8. 修改某个字段后，后续调用的函数、检索条件和任务内容是否正确使用修改后的信息。

重点检查复杂需求在结构化之后有没有失去原本的意义，而不仅仅是字段提取是否正确。

## 2. Context / 项目与轮次语境理解

1. 是否能够理解新需求与已有项目之间的关系，正确判断是新增子项目、继续推荐、针对已有香精进行修改，还是复寄样品。
2. 是否能够结合历史实推香精、客户反馈及原始需求理解诸如“上一款”“第二支”“再清新一些”“还是之前那个方向”等表达。
3. 是否能够正确承袭上一轮仍然有效的要求，同时识别本轮新增、改变或取消的要求。
4. 是否能够区分系统推荐过的香精、评香选中的香精和实际寄出的香精。
5. 客户明确拒绝过的香精是否在后续推荐中得到合理处理。
6. 一个项目经历多次推荐、改香、寄样之后，是否依然能够方便地理解整个项目的历史与当前需求。
7. 调香师的内部试作迭代与客户推荐轮次是否保持独立。

建议选择具有较长历史的真实项目，逐轮输入，而不是仅仅把完整历史一次性交给 LLM 进行理解。

## 3. Targeting / 推荐目标构建

1. LLM 是否真正理解了客户想要的香气、产品定位和商业目标，并将这些信息合理转化为 ABC 目标。
2. 对于直接描述香气的需求和需要理解品牌理念的需求，是否采取了适合各自的 Targeting 方式。
3. 是否正确运用了应用品类对于 C 标签的约束，以及 C 对于 A/B 的关联映射。
4. 是否充分利用已有标签体系，而不是产生大量看似合理但实际无法参与检索的自由文本。
5. 是否保留了客户明确提出的香气要求，避免这些要求在 C→AB 的推导过程中被稀释或覆盖。
6. 当客户的描述存在多种合理理解时，生成的推荐目标是否具有适当的包容性，而不是过早地缩小推荐范围。
7. 评香是否能够方便地理解、修改和补充推荐目标，修改之后是否能立即重新进行筛选和排序。

对于 Targeting 的测试，尤其要关注一个有经验的评香人员是否会认可这种对于客户需求的转译方式。

## 4. Recommendation / 香精筛选与排序

1. 不同 Mode 下的筛选逻辑、ABC 使用方式和权重设置是否符合原本的设计目的。
2. 品类、价格、新品、爆品、品牌目录、大牌仿香等筛选条件是否正确发挥作用，是否存在无意中缩小候选范围的问题。
3. 是否正确区分硬筛条件和匹配偏好，避免因为非关键偏好而排除有价值的香精。
4. C→AB 的映射是否确实能够补充推荐依据，是否存在重复计分、过度推导或不合理的权重倾斜。
5. 实际呈现的前若干款香精是否符合需求，排序上的差异是否具有可以理解的原因。
6. 对于标签缺失、历史应用记录不足的香精，是否有合理的处理方式。
7. 当没有合适结果时，评香是否能够迅速发现问题出在哪里，并通过少量操作调整条件。
8. 指定产品的精确检索是否与基于香气相似度的推荐保持独立。
9. 推荐界面是否提供了评香真正需要的判断依据，而不是仅仅呈现一个综合分数。
10. 手动修改香精标签、查询目标、筛选条件之后，结果的变化是否符合预期。

### 关于历史选香案例的测试方式

选择不同类型、不同品类的真实历史工单，使用当时的客户需求构建推荐目标，尽可能还原当时的选香条件，再观察推荐结果。注意不要直接利用该工单的实推结果构建本次查询或香精标签，否则容易形成循环验证。

逐个分析历史实推香精为什么被选中，在当前系统中的表现如何，是否有其他推荐结果同样合理甚至更有价值。

如果历史选香没有得到很好的排序，进一步思考是 Parse、Targeting、香精标签、品类筛选、权重算法还是数据本身的问题。

历史评香结果不是唯一正确答案。我们需要理解历史选择，而不是单纯提高历史香精的命中率。

## 5. Workflow / 完整业务流程

1. 是否能够流畅地按照 Wanted 结合改进后的流程进行分支使用，模拟一个评香人员的动作是否符合常理。
2. find_product、with_sample、recommend_simple、recommend_brand、modify、dup/仿香、create/创香和 invent/主动开发等路径是否完整。
3. 各条路径是否合理复用了公共模块，而不是在不同分支下形成多套略有区别的重复逻辑。
4. 评香是否能够自主决定继续检索、直接选香、跳过检索、启动开发或暂存项目。
5. 多款香精的需求是否能够被灵活处理，例如一部分从库内选择、一部分创香、一部分改香。
6. 开发任务是否能够正确承袭父项信息，开发完成后是否能够将成果返回到原本的业务语境。
7. 仿香是否正确经过分析环节，原创创香是否能够直接进入调香，改香是否能够关联正确的原配方。
8. 调香结果未达到预期时，是否能够自然地进行下一次迭代，并保留此前的试作和验收记录。
9. 开发完成、评香通过、正式入库、客户交付等不同业务终点是否得到正确区分。
10. 每一次业务推进是否都有真实的对象和数据支撑，而不是单纯改变页面上的状态文字。

## 6. Checking / 应用、合规及质量检查

1. 是否能够根据审查品类、销售地及实际情况生成合理的默认检查要求。
2. 是否能够从 brief 中理解客户额外提出的检查要求，并与默认要求正确合并。
3. 应用品类与审查品类是否在各自适用的环节发挥作用。
4. 已有检查记录是否能够被正确核销，是否考虑香精版本、适用品类、销售地、添加量、测试条件等影响因素。
5. 是否只对尚未获得有效结果的要求生成新的任务，是否能够避免重复检查和重复派发。
6. 检查要求是否被合理地分配给应用、合规及质量部门，派发内容是否足够具体，部门是否能够依据工单直接开展工作。
7. 部门部分完成任务时，是否能够逐项回流结果，而不是等待整个部门任务全部结束。
8. 新获得的检查结果是否能够沉淀为香精资产，之后在其他项目中复用。
9. 开发入库后的二查是否能够复用一查结果，并补充具体客户所需的检查。
10. 对于检查不符合、无法判定、尚未检查、正在检查等情况，系统是否有明确区分和合理的处理方式。
11. 初寄样、正式寄样、入库的放行条件是否符合各自的实际业务要求。

虽然目前缺少真实的香精检查记录，也应该通过模拟中台建立若干完整的检查结果，并测试这些结果能否在不同项目、不同检查条件下得到合理复用。

## 7. State / 状态机与异常处理

1. 是否存在因为一个非关键字段缺失而导致整个项目无法继续使用的情况。
2. 当某个部门任务尚未完成时，评香是否依然能够进行其他不依赖该任务的操作。
3. 多个子项目、多款香精及多个部门任务是否能够相对独立地推进。
4. 暂存、离开页面、重新进入项目之后，是否能够恢复到合理的工作状态。
5. 等待样品、部门反馈或客户信息时，相关信息到达之后是否能够自然恢复流程。
6. 已经确认过的信息是否需要被不必要地重复确认。
7. 修改需求、替换香精或修改配方之后，是否能够正确保留仍然有效的工作成果，并重新处理已经失效的部分。
8. 是否允许评香返回上一步进行合理修改，而不是只能沿一条固定路径单向推进。
9. 对于错误操作、重复提交、重复回流、任务取消等实际使用中可能发生的情况，是否能够妥善处理。
10. 项目是否能够在达到实际业务目标之后正确结束，并在收到后续反馈时重新进入工作流程。

状态机的目的应该是维护业务秩序和信息连续性，而不是限制评香的行动自由。重点检查限制一个操作是否真的有必要。

## 8. Dispatch & Adapter / 部门派发与模拟中台

1. 模拟中台是否具有独立的使用界面，是否能够看到各部门接收到的实际任务。
2. 每一个派发任务是否包含执行人员真正需要的信息，包括原始要求、对象、样品、配方版本、相关附件及预期产出。
3. 是否能够从模拟中台提交分析报告、调香成果、检查结果、入库确认和寄样记录。
4. 这些信息回流之后，评香平台是否能够正确理解、展示、存储并推进流程。
5. 是否支持多个部门并行工作以及任务结果以不同顺序回流。
6. 模拟中台中的价格、库存及其他外部数据发生变化之后，评香平台是否能够正确获取新信息。
7. 模拟中台是否真正通过 Adapter 与评香平台进行通讯，而不是为了演示效果直接修改评香平台内部数据。
8. 未来接入实际中台时，是否能够主要通过替换 Adapter 完成，而不需要重新改写业务流程。

## 9. LLM / 模型选择与多模态能力

1. 每一个 LLM 节点所选择的模型是否能够在保持良好理解能力的同时尽可能快速响应。
2. 模型是否适合当前具体任务，而不是笼统地为所有节点选择一个能力最强的模型。
3. 对于同一类任务，尝试不同模型及是否开启 Reasoning 的配置，观察它们在实际案例中的表现差异。
4. 模型输出是否稳定地满足所需 Schema，同时具有足够的语义理解能力。
5. Prompt 与提供给模型的上下文是否合理，是否存在大量无关信息、重复信息或重要信息缺失。
6. 是否能够区分由于模型能力不足产生的问题和由于 Prompt、资料、Schema 设计不合理产生的问题。
7. 尝试使用案例中的多模态输入进行测试，例如客户截图、产品图片、聊天记录、PDF 或其他附件，观察是否能够结合文字正确理解需求。
8. 图片和附件中的有效信息是否能够进入后续业务字段，而不是仅仅产生一段独立的图片描述。
9. 模型调用失败或返回不完整结果时，是否能够重试、保留已有信息或由评香继续手动操作。
10. 是否能够方便地独立测试和更换某一个 LLM 节点的模型及 Prompt。

模型试验的重点是理解不同模型在哪些具体任务上表现得好或不好，以及其响应速度是否适合实际使用场景。

## 10. UI / 评香实际使用体验

1. 一个没有参与平台开发的评香人员是否能够理解页面内容，并自然地知道下一步应该做什么。
2. 页面展示的信息是否与当前工作的目的有关，是否有大量不必要的解释、状态、字段和按钮。
3. 是否将用户当前需要做的判断与系统可以自动完成的工作合理区分。
4. 是否存在同一个信息被反复填写、反复确认或需要在多个页面之间来回寻找的情况。
5. 常用操作是否足够简洁，少数复杂操作是否能够在需要的时候展开。
6. 按钮的名称是否直白、准确，是否能够反映点击之后真正发生的事情。
7. 推荐、对香、开发、验收、检查、寄样等不同场景是否有各自合适的工作界面。
8. 评香是否可以随时看到有价值的历史信息、原始 brief、香精详情和相关任务进展。
9. 多子项目、多轮次、多款香精同时存在时，界面是否仍然清晰。
10. 是否存在程序逻辑正确，但实际使用起来十分笨拙的环节。

UI 的验收需要完整地操作平台，而不是通过查看静态页面或截图完成。尽可能模拟真实评香一天中连续处理多个项目的情况。

## 11. Feedback / 数据回流与持续优化

1. 评香是否能够随时查看和手动修改香精的 ABC 标签，修改是否真正进入本地正式香精数据并影响后续推荐。
2. 同一香精在不同应用品类下的 C 标签是否能够独立维护。
3. LLM 对需求的 Parse 或 Targeting 不理想时，是否能够方便地进行手动修正。
4. 修正后的结果是否能够立即用于当前项目，同时保留原始输出和修正记录，以供后续分析。
5. 是否区分香精资产的直接更新与 LLM 能力的优化素材，避免单个案例的修正直接影响其他项目。
6. 历史选香、实际寄样和客户反馈是否得到合理沉淀。
7. 推荐模块是否具有独立的数据回流、案例测试和优化机制。
8. 检查结果是否能够在后续项目中产生实际价值，使平台随着使用逐渐减少重复工作。

关注这个系统在使用一段时间之后是否真的会积累有价值的知识，而不是仅仅积累越来越多的工单。

## 12. Architecture / 工程结构与可维护性

1. 项目中的模块、对象和函数是否具有清晰的归属，是否可以通过目录迅速理解工程结构。
2. Workflow 中每一步是否能够对应到实际存在的对象、字段和函数。
3. 函数的输入输出是否明确，是否存在没有来源的输入字段、没有去向的输出字段或隐含的数据传递。
4. LLM、业务字典、计算算法、状态机、数据库操作等不同性质的工作是否得到合理分离。
5. ABC 推荐和检查模块是否具有足够的独立性，是否能够脱离完整项目流程进行测试、调用和维护。
6. 是否能够独立修改标签字典、C→AB 映射、筛选模式、权重、检查要求、部门映射、Prompt 和模型配置，而不影响无关模块。
7. 本地数据、中台数据、原始资料、清洗数据、人工修正记录及研究产物是否有明确的存放位置和权威来源。
8. 说明文档是否与实际实现一致，是否能够通过说明快速找到需要修改的函数或配置。
9. 是否能够观察关键 LLM 节点的实际输入输出、推荐计算过程、检查核销依据及任务状态变化，以便定位问题。
10. 工程是否存在不必要的抽象、重复建设、废弃文件或过度复杂的依赖关系。

以我一人能够理解和维护整个项目为前提，不要以文件数量、代码规模或架构复杂程度体现工程质量。

## 13. End-to-end / 综合案例验收

除了针对上述各模块单独测试，还需要选择具有代表性的完整案例，尝试从原始需求一直推进到最终业务终点。

案例应当覆盖：

1. 信息充分、能够快速完成的简单推荐。
2. 信息较少、需要主动理解品牌定位的复杂推荐。
3. 包含多种产品、多个子项目及不同交付目标的客户需求。
4. 具有明确目标产品的精确检索。
5. 带有实物样品的对香需求，以及直接启动仿香的情况。
6. 经历多次调香、评香验收及检查的开发项目。
7. 同时需要库内选香、创香和改香的项目。
8. 有部分历史检查记录，需要核销和补充派发的项目。
9. 初寄样后收到客户反馈，并继续推荐或改香的项目。
10. 包含图片、文档、聊天记录等多模态资料的项目。
11. 存在信息缺失、等待、修改需求及异常任务的项目。
12. 无客户交付需求、以正式入库为终点的主动开发项目。

优先使用真实案例。真实案例未覆盖的流程可以构造符合实际业务情况的案例，用于检查链路是否完整。

## 14. Review / 验收记录与反思

不需要撰写大量证明功能已经完成的文字，也不需要每个案例都有形式完全一致的报告。

对于值得分析的案例，说明原始需求、实际操作过程中发生的事情、关键判断及其合理性、发现的问题，以及可能的优化方法。

尤其关注：

1. 系统对于需求和业务语境的理解是否有价值。
2. 评香在哪些环节得到了真正的帮助。
3. 哪些环节给评香增加了不必要的工作。
4. 哪些问题具有普遍性，值得调整正式实现。
5. 哪些问题只是个别案例的特殊情况。
6. 完成优化后，之前表现良好的案例是否依然能够顺利进行。

可以将大量重复性操作、模型试验和案例观察交给 DSH，但核心问题的归因、优化方案的选择及最终是否纳入正式系统，由统筹 Agent 作出判断。
