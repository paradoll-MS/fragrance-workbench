# 节点检查手册

更新：2026-10-29  
目的：评香/产品可以自己核对每个 LLM 节点用了什么 prompt、参考了什么、输出了什么，而不是只看最后结果。

## 1. 全局顺序

```text
文件/图片/音频/PDF
  → 解析（pypdf/vision/ASR）
  → 自动分类（classify_artifact.md）
  → 项目简报（extract_brief.md）
  → 拆子项目（split_subprojects.md；有明确建议方向时按方向拆）
  → 品类映射（category_map 规则；map_category.md 兜底）
  → 目标 C 映射（map_c.md，可多选）
  → 硬筛（新类/价格/A1A2A3/品牌/产品）
  → C 计分（每个目标 C +3）
  → AB 计分（每个 distinct +1）
  → 推荐表/短名单
  → 部门任务
  → 终点检查（默认指标 + 客户指定项）
```

## 3. 从界面检查

1. 打开项目 → 资料：每份资料的来源/角色/备注/解析状态；失败会有 `parse_error`。
2. 项目简报：点开完整 JSON/证据；`generation_mode=llm` 表示全量 LLM，`heuristic` 表示兜底。
3. 子项目：顶部“子项目简报”是独立 brief；看 `direction`。
4. ABC 映射：看 A1/A2/A3、目标 C（可多个）、C 固定 AB；C 是候选自己的归属。
5. 推荐：看 C 分/AB 分/总分；`c_json` 记录候选 C 归属。
6. 终点：客户指定项置顶红色；展开看每条 detail；`source=customer`。
7. 项目头部“LLM 日志”：每次调用的 node/provider/model/tokens/成本/耗时。

## 5. 从数据库检查

`data/app.sqlite3`：

- `artifacts`：原文/视觉文本、status、parse_error、source_type/role/note
- `briefs`：项目简报；`subproject_id` 非空的是子项目简报
- `subprojects`：direction/target_cs_json/a1_json/a2_json/a3_json/c_weight/ab_weight
- `recommendations` / `recommendation_items`：filters、c_json、c_score、ab_score
- `endpoint_checks`：source/detail/status
- `llm_calls`：node/provider/model/tokens/cost/elapsed

## 6. 检查全局逻辑是否走对

按这个顺序核：

1. 原文是否真的有文字/视觉文本？没有就先修解析，不要怪简报。
2. `artifacts.source_type/role` 是否符合资料性质？
3. `briefs` 的 `product.category_l3`、`product.target_audience`、`scent.directions`、`scent.direction_notes`、`compliance.regulatory` 是否分开？方向备注是否进入对应子项目，而不是只留在 open_questions？
4. `subprojects` 的方向数是否等于客户建议方向数？
5. 每个子项目是否有 `brief_id` 和独立 brief？
6. `new_class` 是否一致？C 是否同新类？
7. 推荐 `filters_json` 是否用了当前 C/价格/A1A2A3？
8. C 分、AB 分、总分是否是 `C×3 + AB×1`？
9. 终点 `source=customer` 是否置顶且原文明细保留？

## 7. 常见误判

- 图片没文字：先看 `artifacts.status` 是否 `parsed`，再看 `parse_error`。
- 分类为“其他”：检查是否只有图片、没有视觉文本；现在上传即自动视觉+分类。
- 简报空：看 `generation_mode`，若是 heuristic 说明 LLM 超时，规则预填至少不为空。
- 推荐 0：看 `new_class`、目标 C、价格上限、A1/A2/A3；不要先怀疑模型。
- C 分不对：检查 `target_cs_json` 和候选 `c_json`，C 分按目标 C 命中数计。
