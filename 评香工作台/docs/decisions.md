# Decisions ／ 关键取舍

只记会反复被问的取舍，以及为什么不是另一种做法。

## 1. 重搭而不是继续打补丁

第一版有八个结构性问题，补丁解决不了：

- 没有 Subproject、CheckSet、Requirement、Evidence、ReleaseDecision，这些业务对象被压进 `flow_goals.spec`、`flow_slots.context` 和 `tasks.result` 三个 JSON 字段。
- 功能契约 F13–F24 没有实现，检查和放行被跳过，寄样直接由布尔值决定。
- 规则写死在代码里：`validate_draft` 里一百多行正则，含 TF 白麝香、PR_0060、全系列、交期锚定等个案特判。
- 状态机是 8 个字符串加一个 `paused` 布尔，前置条件用 `ValueError` 抛，页面只能看到「该步骤的条件尚未满足」。
- 分层失效：`workflow.py` 43 KB 同时做建表、校验、业务规则、模拟派发和页面投影；`server.py` 24 KB 同时做 HTTP 与建表。
- 两套寄样概念（`decisions` 与 `flow_shipments`）并存，页面上看到的与实际记录的不是一回事。
- 残留文件与旧路由让「当前版本」难以判断。
- 前端 1,260 行，`get`、`el`、`button`、`api` 各重复三次，入口词汇抄了四份。

重搭的代价是一次性重写，收益是对象、契约、规则、页面各自有唯一落点。现在改一条检查规则不用碰页面，接真实中台不用碰业务。

## 2. 阶段只有六个，放行是记录

目标位阶段是 planned / developing / checking / shipping / complete / cancelled。「已放行」不是阶段，因为同一阶段内可以多次放行（初寄、正式、复寄），放行是不可变的事实，阶段是可变的进度。把放行做成 `release_decision` 行之后，回看「谁在什么时候放行了什么」不需要翻审计。

## 3. 要求状态只由证据改

第一版里，点一下「放行」就把任务结果当成通过。现在要求的状态只有两个来源：部门回执落成的证据、人工补录的证据。放行动作只读状态，不写状态。这样：

- 同一份证据可以复用到新清单，不用重复送检；
- 放行未通过时不会把要求「顺手」标成通过；
- 证据冲突时显式标 needs_review，而不是取最新一条。

## 4. 初寄样可以缓，正式寄样不能缓

初寄样是给客户看方向，允许带暂缓项，但必须在备注里写清缓了什么；正式寄样是交付，任何未核销项都不放行。不可暂缓的只有 IFRA、市场法规、过敏原、额外要求——这几项寄出去就可能违规，事后补不了。

另一种做法是「一律不许缓」，实际会逼着人绕过系统先寄再说。允许缓但留痕，比假装严格更接近真实工作。

## 5. 阻断用 Issue，不用异常

业务上的「还不能做」是常态：样品没到、部门没回、清单没生成。这类情况返回 `issues[]`（原因码、缺什么、等什么、下一步），页面据此置灰按钮并显示原因。

但有一类特殊情况：动作确实执行了，业务结论是「不放行」。这时写一条 `release_decision`（verdict = blocked），然后抛 `StepBlocked`，在命令边界转成 `{blocked: true, issues}`。用异常是为了不在每个 handler 里判返回值，用边界转换是为了不把异常泄漏给 HTTP。

参数非法、对象不存在、越权仍然抛 `ValueError`，映射成 400。三种情况语义不同，不能混。

## 6. 规则只读，不自动判定

审查规则文件明确禁止自动判定数值（`dispatch_rules.no_numeric_defaults`）。所以系统只生成「要测什么、按什么口径记录」，合格线来自部门回执或客户标准。曾经想过按品类内置阈值，但那等于替业务下结论，且规则文件里没有这些数。

## 7. 只有两个 LLM 节点

拆解（资料 → 方向）和打标（描述 → 标签）是仅有的两个模型调用点，都在 `app/intelligence/`。模型只产出提案，写库前一定经过人工确认或字典匹配。选香的文字解析不调模型：`ranking.parse_text` 在本地认品类、价格、标签、品牌、产品与版本，认不出的忽略。这样断网也能用，模型只在真正模糊时介入。

## 8. 证据复用靠条件键

证据的匹配键是「香精 + 版本 + 指标 + 子项 + 条件键」，条件键由审查品类、市场、基质、用量等算摘要。这样同一款香精在不同项目、不同清单里都能复用，而换了用途（比如从洗发水换到沐浴露）不会误用。

代价是条件键必须稳定：字段顺序、单位写法变化会导致匹配不上。所以 `conditions_fingerprint` 只取影响结论的字段，并统一小写与去空白。

## 9. 中台隔离在适配层

`PlatformPort` 定义派发、待办、状态、回执、报价、库存、预留、默认回执。本地用 `MockPlatform` 实现，外部编号带 `MOCK-` 前缀。业务层只认协议，接真实中台时替换实现，不改 `workflow`。

模拟中台的回执故意做得很简单：一个部门一条，通过或退回，检查项整组同结论。真实中台的细颗粒度以后再说，现在不假装。

## 10. 写操作带 revision

目标位与项目都有 `revision`，页面提交时带上读到的值，不一致返回 400。单机也会有两个人同时开两个标签页的情况，静默覆盖比报错更难查。

## 11. 前端不引框架

三个页面、一个公共文件、原生 DOM。没有构建步骤，改完刷新就生效，部署就是复制目录。代价是手写 `h()` 与事件绑定，收益是没有工具链、没有版本升级、没有打包产物。

## 12. 动作必须在当前阶段的清单里

`gates.ACTIONS` 是阶段能力的唯一来源。`advance` 先查这张表，不在表里就直接报「当前阶段不能执行该动作」。以前靠各自的 guard 兜底，结果旧页面能越过流程：检查还没做完就能寄样，开发没验收就能入库。白名单比在每个 handler 里重复判断更不容易漏。

代价是新增动作要同时改 `ACTIONS` 和 `TRANSITIONS`，但这正是希望被看见的地方。

## 13. 入库改名，证据跟着改键

试作编号是调香内部的，入库时才定正式编号与版本。如果只改槽位不改证据，父项二查会认为「换了一款香精」，把刚测过的 11 项全部重派。

所以 `accept_warehouse` 在编号或版本变化时，把同一 `(香精, 版本)` 的证据一起改键，并写一条 `rename_fragrance` 审计。前提是这批证据属于当前清单；真要换配方，应该先重建清单再入库，旧证据不会被带过去。

## 14. 需求分两层，方向只写差异

把客户资料拆成「项目级条件 + 方向差异」两层，而不是每个方向各存一份完整需求。原因是人群、市场、法规、添加量通常只出现一次，复制到每个方向会漂移；而香气描述、参照样、排除项确实按方向不同。

`round.brief` 留两层原文，`goal.fields` 存继承后的结果，`parse_draft.result` 留模型原样。三处都能回看，出问题时能判断是模型漏了、归一丢了，还是继承覆盖错了。

代价是字段多了一层合并逻辑；收益是法规原文只出现一次，方向不会因为漏抄人群而失去筛选条件。

## 15. 打标只选 C，A/B 由字典展开

C 是带品类和维度的商业定位，A/B 是气味与联觉词。让模型直接输 A/B 会绕开 C 的判定语境，同一个「花香」在洗发水和线香里含义不同。

所以 `tag_direction` 只让模型在**本品类的 C 叶子**里选，候选带 `C左侧判定补充`，选中后再用 `C到AB关联映射` 展开。模型给的依据必须能在客户原文里找到；找不到的进 unmapped，不采纳。

模型不可用时退回词面匹配，仍能出 A/B 组，只是不带 C 的语境。打标失败不是阻断，页面上能看到 `method` 和 `unmapped`，评香可以手工改标签。

## 16. 明确不做的

- 多用户、权限、登录：单机单人使用，审计留 `actor` 字段即可。
- 真实库存与物流：只做预留与记录，不接 WMS。
- 自动判定合规：只给要求与证据位，不给合格线。
- 删除项目：只改状态，保留追溯。
- 数据同步：一个本地库，不做云端。

这些不是遗漏，是当前阶段刻意不做。等真实使用暴露需求再补，避免先造一套用不上的机制。
