# 中央闻香库第二轮：历史工单补标（轻量执行版 V2）

## 1. 任务目标

在第一轮香精资产之上，利用历史工单中的实际应用、客户需求、选香行为和反馈，为中央库香精补充品类及原生 ABC。当前阶段有＞准：合理的历史推荐关系和市场语境推断即可形成 trial 标签并参与检索，不要求逐款实测、逐标签证明或人工确认。避免明显错配，而不是追求每条推断都可被严格证明。

输入：`香精工单.sqlite3`（只读）、`品类与ABC标签体系_V2.xlsx`、第一轮输出 `fragrance.jsonl` / `fragrance_tags.jsonl` 及身份合并规则。第一轮未完成时，可按有效中央库编码独立生成增量，待第一轮完成后合并。

本轮不重做名称清洗，不重新核验品牌产品，不修改新品/爆品/仿香目录属性，不修改原数据库和标签字典。

**执行原则：一张工单、一次综合 LLM 判断、一次结构化返回。** Agent 负责搭建和运行批处理程序，不亲自逐行调用工具。让 LLM 直接理解工单、判定方向和香精归属、推断标签；不要将这些语义动作拆成多个模型调用，也不要为 C 搭建复杂关键词决策程序。

## 2. 程序准备工单上下文

以工单为任务单元；无工单归属的中央库编号提及，以项目＋备注为补充单元。单张工单包含多款香精时共同处理，不按香精重复解析。先处理有实际用样的工单，再处理仅正文提及的记录；已覆盖的证据不重复派发。

数据连接沿用实际数据库：

- `work_orders.project_id → projects.id`；`sample_occurrences.work_order_id → work_orders.id`；`sample_occurrences.formula_id → formula_refs.id`。以 `formula_refs.code` 精确关联第一轮有效中央库编号；不按名称或编号前缀合并。保留非中央库用样供模型理解分组，但只输出中央库增量。
- `notes`、`note_links.work_order_id/sample_id`：收集本轮需求、评香、用样指令、反馈等；保留备注与样品关联。项目 brief 只作相关背景，重复文本去重；不要把整个项目的全部需求强加给本轮。
- `formula_mentions`：补充正文明确提及的中央库编号。由模型判断它是实际推荐、修改基底、参照、排除还是其他角色。只有提及不能证明已被推荐。
- `directions`、`direction_links`、`library_history_reviews`：如存在相关信息则提供简要辅助；旧 trial 审核不是 V2 正式标签，也不要求模型逐条复核旧审核。
- 物流、法规、稳定、表现力等信息只保留理解用途、用样行为所需部分；去除地址、电话等无关信息。附件未提供不猜内容。

统计基线供核对（原数据库快照）：3566 工单、2578 项目、10819 用样行；中央库标记的 3832 个 formula_refs 中，1358 个有实际用样（5114 行、1233 工单），另有116个仅正文提及。522款出现在多个旧工单品类中。实际任务数量以有效编码及去重结果为准，不硬编码此统计。

### 2.1 单次调用的输入

程序构造紧凑 JSON，示意如下（字段可省略空值）：

```json
{
  "task_id": "work_order_id",
  "old_category": "工单原品类",
  "title": "工单标题",
  "project_context": "相关背景",
  "notes": [{"n": 1, "kind": "work_requirement", "text": "原文", "samples": [1, 2]}],
  "samples": [{"s": 1, "code": "库存编码", "name": "内部名", "customer_name": "对客名", "in_library": true, "prior": {"categories": [], "A1": [], "A2": [], "A3": [], "B": [], "C": {}}}],
  "mentions": [{"s": 3, "code": "正文提及的有效库存编码", "n": 1}]
}
```

`n`、`s` 为本任务内简短整数，程序保存其与真实 note_id、sample_id、fragrance_id 的对应。模型不复述长编号和原文。对同一香精多个用样行保留可区分的引用。第一轮已知标签用于消歧与辅助推断，而非要求逐条检查；即使未提供一轮标签，模型也可以依靠原始工单工作。

### 2.2 字典如何加载

统一规则和字典可作为缓存前缀或共享静态上下文；不要让每个子 Agent 自行读取整个 Excel。运行时只给：

- 12个标准品类的 ID＋中文；AB 的精简 ID＋中文＋必要别名，原则上允许读取全部精简 AB，避免关键词预召回漏掉隐含风格、感官及复合香调。
- 与工单可能涉及的品类相关的完整 C 树（路径、闸门、叶子），加上这些节点真正需要的左侧判定说明。不要重复每个节点的全局规则。
- 品类明确时仅加载相关树；跨品类或品类不明时宁可多加载几个可能品类的树（必要时提供全部精简 C 树），不能只按可能错误的旧 category_group 锁死。若模型判断的品类未提供对应树，保留结果，仅对缺失树的 C 做补充调用，不重跑整个工单。
- 不提供 C→AB 关联表、右侧专家问题表、品牌产品目录全表及其他无关材料。C→AB 是检索阶段的知识，不是本轮贴标的依据。

允许使用程序生成的短标签 ID 对照表以节省 token，但必须可逆映射到 V2 正式 ID；不得用自由文本代替最终有效标签。

## 3. 运行时 LLM Prompt（每次只使用本节＋上下文＋字典）

```text
你是香精公司的评香数据标注助手。根据一张历史工单的完整语境，给其中相关中央库香精补充适用品类和 ABC 候选标签。你不负责数据库操作、联网或逐标签审计。

当前是冷启动，有＞准。把评香实际推荐行为视为有价值的弱证据：如果某款香精被推荐给一个明确的需求方向，通常可以合理继承该方向的公共定位、香韵、感受等，不需要客户逐款确认。结合内部名、对客名、第一轮标签及反馈积极推断；对于合理但不完全确定的标签，允许输出。不要为了填满维度硬猜，也不要因没有实测证据而拒绝一切推断。

在一次综合判断中完成以下工作：
1. 判断本轮真实终端应用（原文及用样指令优先于旧品类和项目标题）；识别公共需求、独立方向，以及哪些香精属于哪些方向。允许多对多、跨品类。仅处理本单实际涉及的应用，不广播整个项目的用途。方向不清时仍可补公共品类/定位。纯补库、参照样或排除对象不等同于应用推荐。
2. 理解方向的需求 ABC，再判断可合理归给相关香精的 ABC。公共标签按组返回一次，个别差异单独返回；具体香气不要从其他独立方向随意复制。若一款香精可能近似匹配，优先继承宽泛香韵和定位；名称明显指向某个方向时可以推断具体气味。直接评价可作为更强证据。修改目标不是原香已有属性；负面评价若描述实际存在的气味，仍可作为正向气味证据；明确缺少的属性记录反证，不自动删除已有标签。
3. A1=气味对象，A2=香韵及气味特征，A3=整体香调，B=感官、情绪及审美。可以依据语义和市场常识推断，不把成分宣称等同闻感，不凭单一原料硬推复合香调。
4. C 按真实应用品类分别判断：理解完整路径，必要时经过闸门并参考左侧解释，只输出有效叶子。允许直接理解明确叶子，不必逐层报告判断过程。多维度、多叶子均可命中；不要求填满四维度。场景本身不必然等于其下某个香气偏好，但上下文足够时应积极推断。若只有 AB 或无法选出合理 C，可以不贴 C。不能将其他品类 C 借来使用，不能通过 C→AB 映射或 AB 反推定位。
5. 只输出所给字典中的合法 ID；真实存在但字典表达不了的定位简短记入 gaps，不创建标签。品类不明不妨碍 AB 补标。仅输出相关中央库对象。无需逐标签理由、置信度或原文复述，只需给每组共用的证据备注编号；真正冲突、反证、无法归属或字典缺口才写简短说明。

按约定 JSON 结构直接返回结果；公共标签和个别标签均为本次历史证据支持的标签，是否已在第一轮存在由程序去重。允许返回空组/空标签。不要输出分析过程、Markdown 或额外说明。
```

## 4. 最小模型输出协议（分组式）

```json
{
  "groups": [
    {
      "g": "d1",
      "direction": "简短需求方向名",
      "cat": ["CAT_02"],
      "samples": [1, 2],
      "kind": "recommended",
      "n": [1],
      "query": {"A1": [], "A2": [], "A3": [], "B": [], "C": []},
      "tags": {"A1": [], "A2": [], "A3": [], "B": [], "C": []}
    }
  ],
  "individual": [
    {"s": 1, "g": "d1", "cat": [], "kind": "direct_evaluation", "n": [2], "tags": {"A1": [], "A2": [], "A3": [], "B": [], "C": []}}
  ],
  "counter": [{"s": 2, "n": [3], "tag": "已有合法ID或空值", "text": "明确缺少水汽"}],
  "gaps": [{"cat": "CAT_04", "text": "面部纯果香定位无适当C叶子"}],
  "unresolved": [{"s": 3, "reason": "只被提及，未明确推荐"}]
}
```

约定：

- 空字段可省略；`query` 是方向目标，用于保留工单语义和将来验证 wanted，不直接写给香精。`tags` 才是可继承的香精候选属性。若二者相同可用 `tags_same_as_query: true` 代替 `tags`，不能默认二者相同。
- `groups.samples` 只列真正可共享该组 tags 的中央库对象。不确定具体分组但可继承公共定位的对象另设公共组；不适用某组标签的对象不要列入该组，必要时另建组。重叠组允许，程序取并集。单款香精的新增或修正证据放 `individual`，无须重新输出已在组内的属性。
- `cat` 是真实应用品类集合；C ID 必须属于其中相应品类。`individual.cat` 为空时继承 g 的品类；无 g 时必须明确给出 C 所属品类。对于同款跨品类，C 按标签字典的 category_id 分别落盘；不能将一个 C 写到全部品类。AB 即便品类未知也可输出。
- `kind` 使用 direct_evaluation / selected / recommended / near_match / modification_base / reference_only / rejected / logistics_only / ambiguous。只有实际描述、推荐、匹配或明确应用等支持的标签才能输出；参照、拒绝和修改基底仍可输出原香的真实描述，不继承未实现的目标。证据类型按组记录，只有必要时拆组，不逐标签写说明。
- `n` 是支持整组判断的备注引用。若仅用样行提供线索，n 可空，程序仍可保存样品关联；不捏造原文。第一轮已有证据不是新的独立工单证据，若没有新的历史支持无需复写。
- 不要求每组附置信度；一律 trial，保留 kind 供以后审查。不因 trial 而禁止检索。

## 5. 程序验收、增量合并和运行方式

程序负责展开每组共享标签到成员香精，叠加 individual 标签，将局部引用转换成真实 ID，自动关联原始备注与样品。校验任务归属、中央库身份、品类合法性、AB 层级及 C 叶子/品类对应。程序不判断语义是否正确，不让 LLM 重新审核所有已有效标签。遇到个别非法 ID，保存有效结果、记录非法项，必要时仅修复异常项；不整批重跑。

输出沿用原第二轮的下游文件接口：

| 文件 | 程序生成内容 |
|---|---|
| `work_contexts.jsonl` | task/work_order/project、方向、品类、query ABC、备注 ID |
| `history_relations.jsonl` | fragrance、工单、方向、用样、kind 及备注引用 |
| `history_category_evidence.jsonl` | 每款新增/获得历史支持的应用品类及其依据 |
| `history_tag_evidence.jsonl` | 每款各标签增量及品类上下文、工单、方向、样品、备注、source=history、status=trial |
| `history_counterevidence.jsonl` | 明确缺失、冲突或需要保留的反证 |
| `review_queue` | 字典缺口、身份歧义、确实无法归属等 |
| `merged fragrance/tag` | 与第一轮合并后的主视图；第一轮未就绪则只交增量 |

可选 `history_product_candidates.jsonl` 仅保存工单中明显的新参照线索，不安排联网搜索或确认身份，不阻塞本轮。沿用第一轮品牌产品状态。

证据由程序依据 n/s/g 自动展开并保留原文引用；如需兼容旧 schema 的 confidence 字段，允许 null，不编造置信度。保留 `source_text` 或可追溯的原文引用；备注与样品组合为证据集合，不虚构逐标签的精确来源。

AB 主标签按 fragrance_id+tag_id 去重；C 按 fragrance_id+category_id+tag_id 去重，品类按 fragrance_id+category_id 去重。多条历史依据并存但不重复计分。已有 confirmed/edited 不覆盖、不降级；冲突记入复核。历史推荐品类可进入候选池，但不是合规、稳定性、表现力已通过的结论。保留新品/爆品等目录字段。

### 运行建议

- 优先用程序直接调用快速或低推理开销的 LLM，结构化输出；同一工单原则上一次请求，多工单并发受接口限额控制。无 API 时才由子 Agent 执行同样的紧凑输入与输出，不给每个 Agent 完整业务规范及大字典，不让它自行规划、搜索、反复读写。
- 不把 10–25 张复杂工单塞进一个长调用。默认每次一张，极短工单经试跑后才考虑合批；特别长的工单按完整独立业务方向拆分，仅在必要时做一次公共语境整理，避免拆散关联。
- 每个任务完成立即落盘、校验、记状态；使用 task_id + 输入哈希 + taxonomy_version + prompt_version 作为续跑依据，重启仅处理失败或未处理项。批次只是调度及写盘分组，不等于模型输入批次。
- 先选择约10–20张代表性工单做小规模试跑（普通单方向、多方向、跨品类、旧品类错误、改香、补样、仅编号提及）。测量端到端耗时、调用数、token、输出合法率及新增标签质量；抽查公共标签是否污染无关样品、是否漏掉明显 C 定位。目标是尽量一次判断完成，保留模型的推断广度，不为了提速改成大规模关键词贴标。并发、模型和上下文大小根据实测调整，不预设速度保证。
- 正式运行按任务/品类汇总处理覆盖、标签增量、失败、反证及高频 gap。只抽查典型/异常工单，不要求逐条人工验收。暂不因个别 gap 修改字典。
